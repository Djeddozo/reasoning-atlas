# RA-013 — Windows–Pi offline synchronization (first slice: notes)

Date: 2026-10-26 · Branch: hq-dev/114-ra-013-implement-windows-pi-offline-sync-1026004147 · Environment: Raspberry Pi (dev loop), Python 3, stdlib only.
Status: implemented and tested with automated tests; not yet deployed or exercised between the real PC and the Pi.

## What was built
- `services/atlas/sync.py`: authority and client logic.
  - **Single authority:** the Pi's hub (`/v1/sync/push`, `/v1/sync/pull`) owns `runtime/sync-authority.db` (or `ATLAS_SYNC_DB`). It is Atlas's own file, never the Engine's `hq.db`. A client that sees a different `authorityId` refuses to sync (no silent second primary).
  - **Durable outbox:** every edit or delete on the PC is a row in `sync_outbox` in `runtime/atlas.db` with its own `commandId` and `baseRevision`. Rows are marked `sent` in a committed transaction before the request, so a crash resends instead of forgetting.
  - **Revisions and tombstones:** each accepted change increments the note's revision; a delete is a revision with `deleted=1` that keeps the last body. Pull uses a monotonic cursor (`seq`) and carries tombstones.
  - **Idempotent replay:** the authority stores the result of every command id (`sync_commands`); a resent command returns the stored result with `duplicate: true` and changes nothing.
  - **Visible conflicts:** a command whose base revision is not current is refused; both versions are kept (`sync_conflicts` on the Pi, the outbox row on the PC). Later commands for the same note in the batch are held as conflicts too, so a chained edit can never land on top of the other device's version. The owner picks "Keep this computer's" (resent on top of the Pi's revision) or "Keep the Pi's"; the other version stays in the outbox record.
  - **No upstream credentials on the client:** the PC uses only its own hub session (`runtime/hub.json`, existing RA-030). Commands, outbox rows and the screen's `/api/sync` carry no credential; the authority needs no Engine, GitHub or model credentials.
- `services/atlas/server.py`: `GET /api/sync`, `POST /api/sync/run | notes | notes/<id>/delete | conflicts/<commandId>/<mine|theirs>`.
- `services/atlas/hub.py`: the two authority endpoints behind the existing hub authentication; a batch is applied in one transaction (all or nothing).
- Screen: Systems › Connections › **Synced notes** (also shown when no hub is connected): state (up to date / waiting to send / stale / conflict), last sync, outbox count, both versions of each conflict with the two choices, add and delete, Sync now.
- `modules/atlas.json`: `atlas.notes.sync` (tested).

## Validation (tests/test_sync.py, 11 tests)
| Scenario | Test | Result |
|---|---|---|
| Offline edit, then reconnect | `test_edit_offline_then_sync` | pending → acknowledged, stale flag clears |
| Disconnect during acknowledgment + restart | `test_disconnect_during_acknowledgment_and_restart` | the Pi applied once; after a restart the same command id is resent and answered as a duplicate; revision 2, not 3 |
| Conflicting edits from two devices | `test_concurrent_edits_conflict_visibly` | conflict with both versions on both sides; keep this computer's → revision 3 |
| Keep the Pi's; chained edits held | `test_keep_theirs_and_held_followups` | both local edits held and kept in the outbox, Pi unchanged |
| Tombstones | `test_delete_travels_as_tombstone` | deleted on the other device, body retained |
| All-or-nothing batch | `test_batch_is_all_or_nothing` | an invalid batch writes nothing |
| Wrong authority | `test_other_authority_is_refused` | SyncError, nothing changed |
| No credentials | `test_no_credentials_in_outbox_or_traffic`, `test_round_trip` | no credential in the outbox, the traffic or `/api/sync` |
| Real HTTP path | `SyncOverHub` (3 tests) | PC service → hub round trip; 401 without hub authentication; 400 for a bad batch; the note never enters the Engine database |

Found while testing: an edit chained after a conflicted edit was first applied on top of the other device's version. Fixed by holding later commands for a conflicted note within the batch.

## Limitations and follow-ups
- Only the new synced-notes dataset is covered. The existing insert-only `notes` table (Notes capture), reminders and actions are not synced yet; moving them onto the outbox is the next step.
- Sync runs when the owner presses "Sync now"; a background timer on the PC is a follow-up.
- No retention for `sync_commands` or tombstones (permanent deletion needs a separate design, DATA_MODEL.md).
- Not yet tested between the real Windows PC and the Pi over Tailscale (needs the hub restarted on the new code).
