## Follow-up 3 (owner report: "Update failed: database is locked")
The Pi stayed on d56bea6, so nothing was half-installed. Cause: another Engine process held the database longer than the update's 15-second wait. Fixes: the update runner waits up to two minutes for the database; if installing succeeded but a later step failed, it restarts anyway and reports "installed … and restarted, but a later step failed", so the Pi never keeps new files with old processes; a failure before installing says "nothing was installed" and how to see the reason. Tests cover both cases.

## Follow-up 4 (owner report: "Update 35cad2d not installed: its tests fail on the Pi")
The updater runs the suite in a detached worktree; there git reports no branch, so the new hub test that compared running and disk commits failed only there. The test now sets the starting commit itself. Verified by running the full suite as the Pi does (Python 3.11, detached worktree): 542 tests pass. The update panel now shows the failing test output under "Last update" instead of only its first line.

## Follow-up 5 (owner report: everything installed, but Focus still asks for a newer Engine)
The files were installed but the hub kept running the old code. Cause: the update runs as its own short-lived systemd unit and started the restart script in the background; when the unit ended, systemd stopped that script during its 2-second pause. Fix: the runner installs without the detached restart and then runs deploy/restart.sh itself and waits for it (`restart_and_wait`). Together with the hub's own check (it restarts when the disk is newer than what it runs), a stale hub can no longer last.
